# 智能交互终端调试与原理学习笔记

> 目标：不是只记录“哪里改了”，而是把这次项目里遇到的问题拆成可复用的调试思路。以后遇到白屏、卡死、串口无响应、Flash 放不下、WiFi 不连、字库方框，都能知道该从哪一层开始看。

---

## 1. 嵌入式调试的基本分层

嵌入式系统的问题通常不是“一个函数错了”这么简单，而是很多层叠在一起：

```
上层功能:  AI对话 / WiFi选择 / 时钟 / 日历 / 环境显示
UI层:      LVGL对象、字体、事件回调、刷新任务
任务层:    FreeRTOS任务、队列、延时、互斥访问
驱动层:    USART / SPI / IIC / SDIO / FSMC / RTC
芯片层:    时钟树、中断、Flash、SRAM、启动地址、向量表
外设层:    ESP8266、LCD、触摸、SD卡、传感器
```

调试时不要一上来就猜 UI 或算法。先问三个问题：

1. 程序有没有跑到这里？
2. 外设有没有正确初始化？
3. 数据有没有从上一层传到下一层？

串口日志的价值就在这里：它能把“我感觉卡住了”变成“卡在某一行之后”。

---

## 2. 串口日志：最朴素但最有用的调试手段

这次 Bootloader 白屏时，屏幕完全不给信息，真正救场的是串口打印：

```
[BOOT] start
[BOOT] before sdio init
[BOOT] after sdio init
[BOOT] app stack=...
[BOOT] app reset=...
```

### 原理

串口日志本质上就是 MCU 通过 USART 把字节发给电脑。它不依赖 LCD、不依赖 LVGL、不依赖文件系统，所以很适合放在早期启动阶段。

调试启动问题时，日志要尽量靠前：

```c
boot_log("[BOOT] start\r\n");
MX_USART1_UART_Init();
boot_log("[BOOT] usart ok\r\n");
```

### 怎么插日志

不要只写：

```c
foo();
bar();
```

要写成：

```c
boot_log("[BOOT] before foo\r\n");
foo();
boot_log("[BOOT] after foo\r\n");

boot_log("[BOOT] before bar\r\n");
bar();
boot_log("[BOOT] after bar\r\n");
```

如果只看到 `before foo`，说明 `foo()` 卡死或 HardFault。  
如果看到 `after foo` 但看不到 `before bar`，说明中间代码或中断出了问题。

### 日志位置不要无限增长

系统界面现在改成了可滚动文本框，这是 UI 层面的优化。底层原则是：

- 串口日志用于定位启动和底层问题。
- 屏幕日志用于展示运行状态。
- 日志太多时要滚动或覆盖，不要挤爆 UI。

## 3. Bootloader / App / IAP 的核心原理

你现在的程序已经不是普通单工程裸跑，而是两段式：

```
0x08000000  Bootloader
0x08008000  App
```

上电后 CPU 永远先从 `0x08000000` 开始执行。也就是说先跑 Bootloader，再由 Bootloader 决定：

- App 有效：跳转 App
- 按住下载键 PA0：进入 IAP
- App 无效：进入恢复模式

### App 有效性判断

Bootloader 会读 App 开头两个 32 位数据：

```c
app_stack = *(uint32_t *)0x08008000;
app_reset = *(uint32_t *)0x08008004;
```

它们分别是：

- 初始 MSP 栈顶地址
- Reset_Handler 入口地址

如果 Flash 没烧 App，通常会读到：

```
0xFFFFFFFF
0xFFFFFFFF
```

这就是“没有有效 App”。

### 跳转 App 为什么要改 MSP 和 VTOR

Bootloader 跳 App 不是普通函数调用。App 认为自己是从 `0x08008000` 启动的，所以跳转前必须准备运行环境：

```c
SCB->VTOR = OTA_APP_BASE;
__set_MSP(app_stack);
app_entry();
```

其中：

- `VTOR` 决定中断向量表从哪里取。
- `MSP` 决定主栈从哪里开始。

这一步漏掉或做错，App 可能表面启动了，但一进中断、HAL_Delay、FreeRTOS、LCD 初始化就异常。

## 4. IAP 固件升级流程

IAP 的本质是：运行中的 Bootloader 接收一个新 App，然后写入 Flash。

你的升级包结构是：

```
app.bin
├── header
│   ├── magic
│   ├── version
│   ├── image_size
│   └── image_crc32
└── payload: app_ota.bin
```

### 为什么要有 header

如果只裸传 bin，Bootloader 不知道：

- 这个文件是不是合法固件
- 固件有多大
- 传输有没有损坏

所以 header 的意义是让 Bootloader 能做校验。

### CRC 的意义

CRC32 不是加密，也不是防破解。它的作用是检查数据传输或写 Flash 过程中有没有错误。

典型流程：

1. PC 计算 payload CRC，写入 header。
2. Bootloader 接收 payload，同时计算 CRC。
3. 写入 Flash 后，再从 Flash 读一遍计算 CRC。
4. 三者一致才认为升级成功。

这就是为什么日志里会有：

```
[IAP] recv crc=...
[IAP] verify flash crc
[IAP] update done
```

## 5. STM32 Flash 分区和“为什么不能随便存几十字节”

STM32F407 的片内 Flash 不是想改哪个字节就改哪个字节。Flash 有两个关键限制：

1. 写入只能把 bit 从 `1` 写成 `0`。
2. 想把 `0` 变回 `1`，必须擦除整个扇区。

F407 后几个扇区很大，常见是 128KB 一个扇区。  
所以“保存一个 WiFi 密码”听起来只要几十字节，但如果放在 App 同一个扇区里，擦密码时可能会把一大片程序一起擦掉。

### 这次踩过的路线

一开始尝试：

```
App 区 + 最后 128KB 留给 WiFi 配置
```

这样保存 WiFi 很安全，但大字库放回 Flash 后 App 空间不够。

最后改成：

```
Bootloader: 0x08000000 - 0x08007FFF
App:        0x08008000 - 0x0807FFFF
```

也就是把 Flash 尽量还给 App，用来放大字库。WiFi 记忆交给 ESP8266 自己。

## 6. ESP8266 为什么能自动连接 WiFi

ESP8266 AT 固件内部也有自己的 Flash。执行：

```text
AT+CWJAP="ssid","password"
```

通常会把 AP 信息保存到 ESP8266 模块自己的 Flash。下次启动后，只要开启自动连接：

```text
AT+CWAUTOCONN=1
```

ESP8266 就可以尝试连接上一次保存过的 WiFi。

### 为什么这比 STM32 存 WiFi 更适合当前项目

- 不占 STM32 Flash。
- 不依赖板子有没有 AT24C02。
- 不依赖 SD 卡。
- 不会因为擦配置把 App 擦坏。
- 手动连成功一次后，下次可自动连接。

代价是：SSID/密码存在 ESP8266 里，STM32 不直接掌握这份配置。但对这个项目来说，这个代价可以接受。

## 7. SD 卡为什么做 OTA 和字库都容易出问题

SD 卡看起来容量大、很诱人，但它不是“稳定的片内资源”。它涉及：

- SDIO 时钟
- 1bit/4bit 总线模式
- 卡上电初始化时序
- FatFS 挂载
- 文件路径大小写
- 读扇区重试
- 卡座接触和走线

这次 SD OTA 出现过随机卡在不同位置：

```
mount fail
disk read fail
open fail
read sector timeout
```

这种“每次复位卡的位置不一样”，通常说明问题不是纯软件逻辑，而是底层时序、电气稳定性、总线模式或驱动鲁棒性问题。

所以最后的判断是：

- OTA：优先串口 IAP / WiFi IAP
- 字库：放回 Flash，保证显示稳定
- SD 卡：作为资源扩展可以，但不作为核心启动链路

## 8. 字库方框的根本原因

LVGL 显示汉字不是“字符串是 UTF-8 就一定能显示”。它还需要字体里真的包含这个字的 glyph。

如果字体里没有某个字，显示出来就是方框。

### 这次的变化

之前为了省 Flash，把大字库换成小 UI 字库：

```
菜单 系统 时钟 返回 发送 温度 ...
```

这些字能显示，但拼音输入法候选字有三千多个常用汉字。小字库不包含它们，于是 AI 输入候选和输入框里大量方框。

解决方案是把常用字库重新生成进：

```
LVGL/src/font/lv_font_cjk16.c
```

并在 `freertos.c` 固定：

```c
cjk16_font = &lv_font_cjk16;
```

### 记住这个原则

显示方框时先查两件事：

1. 字符串编码是不是 UTF-8。
2. 当前字体是否包含这个字。

编码对了但字体缺字，仍然是方框。

## 9. FreeRTOS + LVGL 的调试原则

LVGL 不是线程安全的。一般原则是：

> 尽量只在 LVGL 任务里操作 LVGL 对象。

所以 ESP 任务不要直接改 label、textarea。更好的方式是：

```
ESP任务 -> 消息队列 -> LVGL任务 -> 更新UI
```

你现在的系统日志就是这个思路：

```c
osMessageQueuePut(esp_rx_queueHandle, &m, 0, 100);
```

LVGL 任务里再取：

```c
osMessageQueueGet(esp_rx_queueHandle, &m, NULL, 0);
lv_textarea_set_text(status_info_label, status_buf);
```

### 为什么这样做

如果多个任务同时改 LVGL 对象，可能出现：

- 随机卡死
- UI 对象状态错乱
- 偶发 HardFault
- 一些“看起来玄学”的问题

队列方式虽然代码多一点，但稳定。

## 10. 遇到问题时的排查模板

### 白屏 / 灯不闪

先看：

1. 串口有没有 `[BOOT] start`
2. Bootloader 有没有跳 App
3. App 有没有 `[APP] uart ok`
4. 是否卡在 LCD / touch / mem / fatfs / kernel start

如果 App 没日志，先怀疑：

- App 没烧进去
- Bootloader 没跳
- App 地址不对
- 向量表/MSP 不对

### WiFi 一直 Connecting

先分清：

1. ESP8266 AT 是否正常
2. 是否真的在执行 `CWJAP`
3. 是连接失败，还是 UI 没更新状态
4. 是否处在 SoftAP/server 模式没切回 station

相关指令：

```text
AT
ATE0
AT+CIPSERVER=0
AT+CIPMUX=0
AT+CWMODE=1
AT+CWJAP?
```

### AI 回复乱码 / 方框

先看：

1. 云端是否返回 emoji 或特殊符号
2. JSON 解析后是否保留了非法 UTF-8
3. `sanitize_ai_text()` 是否过滤了不支持字符
4. 当前字体是否包含这些字

### IAP 失败

看日志停在哪里：

- `wait command`：PC 没发 IAP 命令，或串口没接对
- `header receive fail`：包头没收完整
- `receive fail`：中途断流
- `crc fail`：传输损坏
- `verify fail`：写 Flash 后读回不一致，或 App 向量非法
- `no valid app`：App 首地址栈/入口不合法

## 11. 当前项目比较稳定的结构

目前更推荐的最终结构：

```
Bootloader
├── 上电判断 PA0
├── 有效 App 直接跳转
├── 按键进入 IAP
├── 串口 IAP
└── WiFi IAP

App
├── FreeRTOS
├── LVGL UI
├── AI 对话
├── WiFi 选择
├── ESP8266 自动重连
├── RTC 同步
├── 环境数据
└── Flash 内置常用汉字字库
```

这个结构的优点是：

- 启动链路短。
- 显示不依赖 SD 卡。
- 升级不依赖 SD 卡。
- WiFi 记忆不占 STM32 Flash。
- 大字库能放回 Flash，AI 输入更稳。

## 12. 后续学习路线

如果想真正吃透嵌入式调试，可以按这个顺序学：

1. **启动流程**：复位向量、启动文件、SystemInit、main。
2. **内存模型**：Flash、SRAM、CCM、栈、堆、ZI/RW/RO。
3. **链接脚本**：scatter 文件如何决定代码放在哪里。
4. **中断机制**：向量表、VTOR、NVIC、优先级。
5. **Flash 编程**：扇区擦除、字/半字写入、CRC 校验。
6. **串口协议**：阻塞收发、中断接收、环形缓冲、帧解析。
7. **RTOS 调试**：任务栈、优先级、队列、互斥、死锁。
8. **LVGL 移植**：tick、timer handler、display flush、indev read。
9. **网络模块**：AT 指令状态机、TCP 流、HTTP 报文、超时重试。
10. **工程化**：日志分级、构建脚本、版本管理、升级包格式。

学到最后，你看一个嵌入式问题时，就不会只盯着“这个函数为什么不行”，而是会自然地想：它卡在哪一层？这层依赖的下一层有没有给它正确条件？
