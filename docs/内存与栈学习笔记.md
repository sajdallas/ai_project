## 一、这次到底发生了什么（总结）

**现象**：拼音输入法 + AI 对话都跑通了，但**连续发到第 3 轮左右必死机**，板上 LED 也卡住不闪了（说明不是 UI 卡顿，是整机崩溃）。

**排查过程（三层）**：

1. 第一层——怀疑 `chat_build_json` 里 `snprintf` 累加越界，修了（这是个真 bug，但不是这次的元凶）。
2. 第二层——用户反馈"还是第 3 次打字输入必崩"，说明是**打字路径**、且**必然发生**，指向内存问题。
3. 第三层——打开 `MDK-ARM\ai_project\ai_project.map`，看到执行区真实占用：**主 SRAM 用了约 110KB / 128KB，只剩 ~18KB**。而 LVGL 内存池只有 20KB。

**根因**：LVGL 内存池（20KB）太小。5 个页面的控件常驻内存 + 对话列表反复"清空重建" + 候选标签反复 `set_text`，把池子**碎片化**到极限 → `lv_mem_alloc()` 返回 `NULL` → 解引用空指针 → **HardFault**。

**四个修复**：

| 改动 | 作用 |
|---|---|
| LVGL 池 20KB → 48KB，搬到 64KB CCM RAM（`LV_MEM_ADR 0x10001000`） | 池不再耗尽，主 SRAM 空出 20KB |
| FreeRTOS 堆 25KB → 40KB | 装得下更大的栈 |
| lvglTask 栈 8KB → 16KB | 键盘+候选栏渲染路径栈吃紧 |
| esp8266Task 栈 4KB → 8KB | HTTP 建包/收包路径栈吃紧 |

下面逐个概念拆开讲。

## 二、STM32F407 的内存地图

单片机里"内存"不是一整块，而是**按地址划分成好多块**，各有各的用途和限制。F407VET6 的关键区域：

| 地址范围 | 大小 | 名称 | 说明 |
|---|---|---|---|
| `0x08000000` | 512KB | Flash | 存程序代码和只读数据，掉电不丢 |
| `0x20000000` | 112KB | SRAM1 | 通用 RAM（本项目 RW_IRAM1） |
| `0x2001C000` | 16KB | SRAM2 | 通用 RAM（本项目 RW_IRAM2），和 SRAM1 合称 128KB |
| `0x10000000` | 64KB | **CCM RAM** | 只能 CPU 访问，**不能 DMA**；零等待，速度最快 |
| `0x40000000` | — | 外设寄存器 | GPIO/USART/SPI/FSMC… 的控制寄存器 |
| `0x60000000` | — | FSMC 外部内存 | 本项目 LCD 通过 FSMC 接在这（`0x68000000`） |
| `0xE000E000` | — | 内核外设 | NVIC/SysTick/MPU… |

几个要点：

1. **CCM（Core Coupled Memory）**：挂在 CPU 内核上的"贴身内存"，速度最快，但**DMA 控制器访问不到它**。所以只能放 CPU 自己读写的东西（对象、变量、栈），**不能放 DMA 缓冲区**。这就是为什么把 LVGL 池搬过去安全——LVGL 池里只放控件对象，不涉及 DMA；而显示缓冲 `buf1/buf2` 走 FSMC（CPU 直接写地址），也得留在 SRAM。

2. **内存是分块的，不是一大片**。写程序时"哪个数组放哪块内存"是能控制的（用链接脚本 / scatter 文件 / `__attribute__` / `LV_MEM_ADR` 之类），这是优化的关键手段。

3. **本项目 F407 的 64KB CCM 之前完全闲置**，等于白扔了 64KB 高速内存——这正是这次能"无中生有"救急的原因。

## 三、程序里的"段"（section）

你写的代码编译链接后，会被分成几个**段**，分别放进 Flash 或 RAM。用 `.map` 文件能看得一清二楚。

| 段 | 放什么 | 存哪 | 谁初始化 |
|---|---|---|---|
| `.text` | 机器代码（函数） | Flash | — |
| `.rodata` / `.constdata` | 常量、字符串字面量、字体位图 | Flash | — |
| `.data` | 已初始化的全局/静态变量（如 `int x = 5`） | RAM | 启动代码从 Flash 拷过来 |
| `.bss` | 未初始化/零初始化的全局/静态变量（如 `static char buf[512]`） | RAM | 启动代码清零 |
| 堆 heap | 运行时动态分配的内存 | RAM | 你的代码/分配器 |
| 栈 stack | 函数局部变量、返回地址 | RAM | 运行时自动 |

关键理解：

- **`.data` 和 `.bss` 是 RAM 大头**。比如 `chat_history[20]`（约 5.4KB）、`http_resp[4096]`（4KB）、`json[8192]`（8KB）、FreeRTOS 堆 `ucHeap[40960]`、LVGL 池——这些全是 RAM。
- **字体是 Flash 大头**。`lv_font_cjk16` 位图约 138KB，但它是 `const`，进 `.constdata`（Flash），**几乎不占 RAM**。所以"字库很大"和"RAM 不够"是两回事。
- **`static` 局部变量也在 `.bss`**（比如 `esp8266StartTask` 里的 `static char json[8192]`），它不占栈，占 RAM——容易误以为它占栈。

### 怎么看 map 文件的真实占用

`ai_project.map` 末尾有执行区（Execution Region）：

```
Execution Region RW_IRAM1 (Exec base: 0x20000000, ... Size: 0x00019b80, Max: 0x0001c000)
Execution Region RW_IRAM2 (Exec base: 0x2001c000, ... Size: 0x00001b68, Max: 0x00004000)
```

`Size` 是**真实用了多少**，`Max` 是这块 RAM 总大小。0x19b80 ≈ 105KB，0x1b68 ≈ 7KB，合计 ~112KB，而总 Max 是 128KB → 只剩 ~16KB。

> ⚠️ 陷阱：别信 `Grand Totals` 里那个 `Total RW Size 1130.79kB`！它把 FSMC 外部内存（`0x68000000`，约 1MB）的 UNINIT 段也算进去了，是"幻影"。**看执行区 `RW_IRAM1/2` 的 Size 才是真相。**

## 四、栈 Stack

### 栈是什么

栈是一块**后进先出（LIFO）**的内存，由硬件自动管理。CPU 有个寄存器 **SP（Stack Pointer）** 指向栈顶。

在 Cortex-M 上，栈是**向下生长**的：栈顶在地址高端，每放一个东西 SP 就往低地址移动。

### 函数调用时栈上会发生什么

```c
void ime_commit(const char *cand, int pinyin_len) {
    char buf[512];              // ① 栈上开 512 字节的局部数组
    const char *text = ...;
    int w = snprintf(buf, sizeof(buf), ...);   // ② 调用 snprintf
    ...
}
```

调用 `snprintf` 时，硬件自动做这些事：

1. 把**返回地址**（调用完该回哪）压栈；
2. 把**参数**（`buf`、`sizeof(buf)`、格式串…）压栈或放寄存器；
3. 进入 `snprintf`，它自己的**局部变量**也开在栈上；
4. `snprintf` 返回时，弹出局部变量和返回地址，回到 `ime_commit`。

**栈的消耗 = 调用链上每一层函数的局部变量 + 参数 + 返回地址之和**。调用越深、局部数组越大，栈用越多。

### 栈溢出（Stack Overflow）

如果栈用超了它被分配的大小，就会**溢出**，写到**相邻的内存**去。这是嵌入式里最常见的死机原因之一。

为什么危险：

- 它**不是立刻报错**，而是**静默破坏相邻数据**。可能把你别的变量、别的任务的栈、FreeRTOS 堆的元数据写坏。
- 症状**随机**：可能这次好的下次崩，可能崩在完全不相干的地方。第 3 次崩、第 5 次崩，往往就是栈/堆被踩了。

判断信号：

- 崩溃点"随机"、不固定；
- 加一句 `printf` 就不崩了（因为栈布局变了）；
- 灯卡住 / HardFault，且难以用逻辑解释。

### FreeRTOS 里每个任务有自己独立的栈

RTOS 不是所有任务共用一个栈，而是**每个任务一块栈**：

```c
const osThreadAttr_t lvglTask_attributes = {
  .name = "lvglTask",
  .stack_size = 4096 * 4,   // 16KB，这块栈从 FreeRTOS 堆里分配
  ...
};
```

所以：

- **栈大小要按"该任务最深的调用链"来估**，还要留余量。
- 本项目 lvglTask 跑 LVGL 渲染 + 事件处理 + 拼音候选栏（`ime_commit` 里还有个 512 字节的 `buf`），调用链很深，8KB 就偏小了 → 加到 16KB。
- 栈、TCB（任务控制块）、队列，**全都从 FreeRTOS 堆（`configTOTAL_HEAP_SIZE`）里分**。所以加大栈必须同步加大这个堆。

### 如何测栈用了多少

- **高水位**：`uxTaskGetStackHighWaterMark(task)` 返回"从没被用掉的最小剩余栈"，可以知道峰值用量。判断标准：**剩余最好 > 栈大小的 20%**。
- **自动检查**：`FreeRTOSConfig.h` 里 `#define configCHECK_FOR_STACK_OVERFLOW 2`，配合 `vApplicationStackOverflowHook`，溢出时能立刻停下，方便定位。

## 五、堆 Heap

### 堆是什么

栈是"函数进出自动管理"，堆是**手动、运行时**申请/释放的内存。

```c
char *p = lv_mem_alloc(100);   // 申请 100 字节
... 使用 p ...
lv_mem_free(p);                // 用完释放
```

### 碎片化（Fragmentation）—— 本次死机的真凶

堆是一整块，但反复"申请小 → 释放 → 申请大"会在中间留下很多**用不上的小洞**：

```
[  A  ][空闲10B][  B  ][空闲8B][  C  ][空闲12B]...
```

这些洞合起来有 30B，但你要申请一个 20B 的块时，**找不到连续的 20B**，于是分配失败。这就是**碎片化**——总空间够，但"连不成一块"。

本项目的触发链：

1. 对话列表 `chat_ui_update()` 每次 `lv_obj_clean(chat_list)` 清空、再 `lv_list_add_text()` 重建若干项；
2. 拼音候选栏每次打字都 `lv_label_set_text()` 改 8 个标签的文本（内部会 free + 重新分配）；
3. 反复几轮后，20KB 的池子被切得七零八落；
4. 第 3 次打字，某次 `lv_mem_alloc` 找不到连续空间 → 返回 `NULL` → 解引用空指针 → 崩。

### 内存泄漏（Leak）vs 碎片化

- **泄漏**：申请了但**永远不释放**。内存只会越来越少，最终耗尽。容易用"内存用量单调上升"判断。
- **碎片化**：申请和释放都在做，但**分布不合理**导致小块无法合并。总用量不一定涨，但分配会失败。

本次是**碎片化**（池太小 + 高频小块分配），不是泄漏。

### LVGL 的内存池

LVGL 默认不用 `malloc`，而是自己管理一块池子（`lv_conf.h`）：

```c
#define LV_MEM_CUSTOM 0
#define LV_MEM_SIZE (48U * 1024U)   // 池子大小 48KB
#define LV_MEM_ADR 0x10001000       // 0 = 用静态数组；非 0 = 直接用这个地址（CCM）
```

- `LV_MEM_SIZE`：池子多大。控件越多、越复杂，越要大。
- `LV_MEM_ADR`：把池子放到**指定地址**。我们用它把池子搬进 CCM RAM，省出主 SRAM。
- 分配器是 **TLSF**（Two-Level Segregated Fit），专门为嵌入式设计，抗碎片化能力较好——但池子太小的话谁都没办法。

### FreeRTOS 的堆

`FreeRTOSConfig.h` 的 `configTOTAL_HEAP_SIZE` 是 FreeRTOS 自己的一块堆，用来分**任务栈、TCB、队列、信号量**。它默认用 `heap_4.c`（能合并相邻空闲块，抗碎片化）。本次从 25KB 加到 40KB 是为了装下更大的栈。

## 六、本次踩的坑（真实案例）

### 坑 1：`snprintf` 累加越界（第一层误判，但确实是真 bug）

```c
int pos = snprintf(json, json_sz, "{\"model\":...");
for (...) {
    pos += snprintf(json + pos, json_sz - pos, "...");   // 危险
}
```

`snprintf` 的返回值是"**本应写入的长度**"（即使被截断也返回完整长度）。一旦 `pos` 超过 `json_sz`：

- `json_sz - pos` 变成**负数**；
- 传给 `snprintf` 的 size 参数是 `size_t`（无符号），负数变成一个**巨大值**；
- `snprintf` 以为缓冲区超大，直接往外面写 → 内存被破坏。

**修法**：每次写完后把 `pos` 钳制在 `[0, json_sz-1]`，越界就 `break`。

### 坑 2：LVGL 池 20KB 不够（真元凶）

见上面"碎片化"。20KB 装 5 个页面（含键盘、列表、候选栏）很勉强，反复操作后崩。

### 坑 3：任务栈太小

lvglTask 8KB 跑 LVGL 复杂界面 + 512B 局部缓冲的调用链偏小；esp8266Task 4KB 跑 HTTP 建包收包偏小。都加大了。

### 坑 4：map 文件的 `Grand Totals` 幻影

`Total RW Size 1130KB` 看着吓人，实际是 FSMC 外部内存 UNINIT 段被算进去了。**看执行区 `RW_IRAM1/2` 的 Size** 才是真实 SRAM 占用。

## 七、排查工具与方法

### 1. 看 .map 文件（最省事，先做）

Keil 编译后在 `MDK-ARM\ai_project\` 下有 `ai_project.map`。搜：

- `Execution Region` → 看每块 RAM 的 `Size` 和 `Max`，判断"还够不够"。
- 具体符号 → 看哪个数组/对象占了多少（`glyph_bitmap`、`ucHeap`、`_lv_mem_pool` 等）。

### 2. HardFault 定位

死机多半进 `HardFault_Handler`（`stm32f4xx_it.c`）。要抓原因，读三个寄存器：

- **CFSR**（Configurable Fault Status Register）：看是"用法错误""总线错误"还是"内存管理错误"；
- **HFSR**：确认是不是 HardFault；
- **SP**：出问题时的栈指针，配合 LR 可以回溯调用点。

在 `HardFault_Handler` 里加一段把 CFSR/HFSR/PC 通过串口打出来，是嵌入式排障的基本功。

### 3. 栈高水位

```c
UBaseType_t hw = uxTaskGetStackHighWaterMark(lvglTaskHandle);
// 剩余 < 栈大小的 20% 就危险
```

把 `configCHECK_FOR_STACK_OVERFLOW` 设为 `2` 也能在溢出瞬间拦住。

### 4. 观察内存用量趋势

- LVGL 有 `LV_USE_MEM_MONITOR`（`lv_conf.h`），能实时看 `lv_mem_alloc` 的峰值和碎片率。
- 如果用量**单调上升** → 泄漏；如果**总用量不大却分配失败** → 碎片化。

## 八、速查表

| 症状 | 最可能原因 | 排查/修复 |
|---|---|---|
| 随机死机、灯卡住 | 栈溢出 / 堆被踩 | 加大任务栈、加栈溢出检查 |
| 反复操作后必崩 | LVGL 池耗尽/碎片化 | 加大 `LV_MEM_SIZE`，可搬 CCM |
| 内存用量单调涨 | 内存泄漏 | 查 free 是否配对、用监视器 |
| 总内存够但分配失败 | 碎片化 | 减小块大小、换分配器、加大池 |
| 发第 N 条消息崩 | 缓冲越界（累积型） | 检查 `snprintf`/数组边界 |
| 符号显示成框框 | 字库没这个字 | 扩字库（生僻字/emoji） |
